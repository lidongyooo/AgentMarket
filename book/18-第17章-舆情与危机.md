# 第 17 章　舆情与危机：当 Agent 犯错的时候

> Agent 一定会犯错。问题不是"会不会"，而是"犯错之后，你怎么做"。

## 17.1 Agent 危机的独特性

所有的公司都可能遇到危机，但 Agent 公司面临的危机有其独特性。

**第一，自主行为带来新型事故。**传统软件出问题，通常是"不能用"——系统崩溃、功能失效。Agent 出问题，可能是"乱用"——它自主地做了用户没有预期的事情：删除了不该删的文件、发送了不该发的邮件、修改了不该改的数据、在公开场合说了不该说的话。这种"主动犯错"比"被动失效"更容易引发愤怒和恐慌。

**第二，截图与录屏让传播极其迅速。**Agent 的错误往往有清晰的"证据"：一段对话截图、一段操作录屏、一条错误的输出。这些证据非常容易在社交媒体上传播。一张"AI 把我的代码库删了"的截图，可能在几个小时内传遍整个开发者社区。

**第三，AI 话题天然具有放大效应。**AI 是当下最受关注的话题之一，任何与 AI 相关的负面事件都容易被放大。媒体乐于报道"AI 翻车"的故事，公众对 AI 的担忧也会让这类事件引发更广泛的讨论。

**第四，"翻车"内容有流量。**在中国的内容生态中，"AI 翻车"已经成为一种受欢迎的内容类型。很多博主专门测试 AI 产品的极限，寻找它们的失误，并制作成视频或文章发布。这意味着 Agent 产品的每一个弱点都可能被放大展示。

**第五，信任一旦受损，很难恢复。**在第 6 章，我们说过信任是 Agent 的第一产品。一次严重的事故，可能让用户和客户对 Agent 的信任瞬间崩塌，而重建信任需要很长时间。

因此，Agent 公司必须比传统软件公司更加重视危机管理。

## 17.2 Agent 危机的八种类型

根据危机的来源和性质，Agent 公司可能面临以下八种类型的危机：

### 类型一：能力翻车

**表现**：产品的实际表现与宣传或演示严重不符。用户发现"演示里很厉害，自己用起来完全不是那么回事"。

**典型场景**：产品发布时的演示被发现经过大量剪辑或人工干预；用户在社交媒体上发布大量"实测翻车"的内容；知名博主发布负面评测。

**风险等级**：中到高。可能导致大规模的口碑崩塌。

### 类型二：行为事故

**表现**：Agent 在执行任务时，做出了造成实际损失的错误行为。

**典型场景**：编程智能体删除了重要的代码或数据；办公 Agent 向错误的人发送了包含敏感信息的邮件；客服 Agent 向客户做出了公司无法兑现的承诺；Agent 执行了用户没有授权的操作。

**风险等级**：高。直接造成用户损失，容易引发愤怒和法律纠纷。

### 类型三：内容风险

**表现**：Agent 生成了不当、有害或违规的内容。

**典型场景**：Agent 生成了含有错误事实、歧视性、违法违规内容的输出；Agent 被用户诱导输出不当内容并被截图传播；Agent 生成的内容侵犯了他人的知识产权。

**风险等级**：高。在中国，内容安全是监管的重点领域，严重的内容风险可能导致监管处罚。

### 类型四：数据安全事件

**表现**：用户数据被泄露、滥用或丢失。

**典型场景**：系统漏洞导致用户数据泄露；Agent 被提示词注入攻击，泄露了用户数据；员工违规访问用户数据；用户数据被发现用于未经授权的目的（如模型训练）。

**风险等级**：极高。可能导致监管处罚、法律诉讼、客户大规模流失。

### 类型五：计费争议

**表现**：用户对计费产生不满和争议。

**典型场景**：用户收到意外的高额账单；自动续费没有提前提醒，或取消困难；额度计算不透明，用户感觉被"坑"；产品降价后老用户感到不公平。

**风险等级**：中。容易引发投诉和负面口碑，严重时可能引发监管关注。

### 类型六：舆论争议

**表现**：公司的言论、产品或商业行为引发社会争议。

**典型场景**：宣传"AI 取代人工"引发就业焦虑的讨论；创始人的不当言论引发争议；产品涉及版权、隐私、伦理等社会议题引发讨论。

**风险等级**：中到高。取决于争议的范围和性质。

### 类型七：合规事件

**表现**：公司因违反法规而受到监管部门的关注或处罚。

**典型场景**：产品未按要求完成备案或登记；内容安全措施不到位；个人信息处理不合规；广告宣传违反广告法；产品被要求下架整改。

**风险等级**：极高。可能导致业务中断。

### 类型八：竞争攻击

**表现**：竞争对手或其他利益相关方发起的恶意攻击。

**典型场景**：有组织的负面评论和虚假信息；断章取义的对比和抹黑；散布不实谣言。

**风险等级**：中。需要冷静应对，避免陷入口水战。

### 产品层面的预防

- **安全设计**：在产品设计中落实"看得见、管得住、撤得回"（见第 6 章），从根本上降低行为事故的风险。
- **红队测试**：定期组织内部或外部的红队测试，模拟恶意用户和攻击者，发现产品的安全漏洞和内容风险。
- **发布前检查**：每次产品发布前，进行安全、内容、合规方面的检查。
- **危险操作保护**：对删除、发送、支付等高风险操作，默认要求用户确认。

### 营销层面的预防

- **期望管理**：坚持诚实的演示（见第 8 章），不夸大产品能力，避免能力翻车。
- **用语审查**：所有对外内容经过合规审查，避免违规用语和争议性表述。
- **计费透明**：清晰的计费规则、用量提醒、预算上限、便捷的取消方式（见第 5 章和第 10 章）。

### 舆情监测

建立舆情监测机制，及时发现潜在的危机：

- **监测范围**：主要社交媒体平台（微博、微信、抖音、小红书、知乎、B 站等）、技术社区、新闻媒体、应用商店评论、投诉平台。
- **监测关键词**：公司名称、产品名称、创始人姓名，以及"翻车""删除""泄露""坑""退款"等与危机相关的词语组合。
- **监测工具**：使用专业的舆情监测工具，或者用 Agent 搭建自己的舆情监测系统。
- **预警机制**：设定预警阈值，当负面信息数量或传播速度超过阈值时，自动通知相关负责人。

### 危机预案与演练

- **危机小组**：成立危机处理小组，明确成员（通常包括 CEO、公关负责人、法务负责人、产品负责人、技术负责人、客服负责人）和职责。
- **危机预案**：针对主要的危机类型，制定详细的应对预案，包括响应流程、决策权限、沟通口径、声明模板。
- **定期演练**：每半年或每年进行一次危机演练，模拟真实的危机场景，检验预案的有效性。

## 17.4 响应框架：危机发生后的五个步骤

当危机发生时，建议按照以下五个步骤进行响应：

### 第一步：确认事实（第一时间）

在采取任何行动之前，首先要尽快确认事实：

- 发生了什么？什么时候发生的？影响了哪些用户？
- 是产品的问题，还是用户的误解，还是恶意的攻击？
- 问题是否仍在持续？影响范围是否在扩大？
- 现在网络上的舆论情况如何？

确认事实要快，但不能草率。基于错误事实的回应，会让危机雪上加霜。

### 第二步：评估级别（第一时间）

根据事实，评估危机的级别：

- **一级（轻微）**：影响个别用户，传播范围有限。由客服和产品团队处理。
- **二级（一般）**：影响一定数量的用户，在特定社区中有一定传播。由危机小组处理，公关负责人主导。
- **三级（严重）**：影响大量用户，在社交媒体上广泛传播，或媒体开始关注。CEO 亲自参与，全公司协调应对。
- **四级（重大）**：造成重大损失，引发广泛的社会关注或监管关注。最高级别响应。

### 第三步：首次回应（尽快）

在中国的舆论环境中，危机发生后的最初几个小时至关重要。如果企业长时间保持沉默，舆论就会被猜测和谣言填满。

首次回应不需要包含所有的细节，但需要传达几个关键信息：

- **我们知道了**：我们已经注意到这个问题。
- **我们重视**：我们非常重视，正在全力处理。
- **我们在行动**：我们已经采取了哪些初步措施（比如暂停相关功能、联系受影响的用户）。
- **我们会更新**：我们会在什么时间之前提供进一步的信息。

### 第四步：处理与补救（持续）

- **解决问题**：尽快修复导致问题的技术缺陷或流程漏洞。
- **补救损失**：对受影响的用户提供补救——恢复数据、退还费用、提供补偿。
- **持续沟通**：按照承诺的时间提供进展更新，保持信息透明。
- **一对一沟通**：对于受到严重影响的用户和重要客户，进行一对一的沟通和安抚。

### 第五步：复盘与沟通（危机后）

- **内部复盘**：深入分析危机的根本原因，总结经验教训，制定改进措施。
- **公开说明**：在适当的时候，公开发布事件的调查结果和改进措施。
- **跟踪落实**：确保改进措施真正落实，并在适当的时候公开进展。

## 17.5 回应的五个原则

### 原则一：速度

在社交媒体时代，速度是危机回应的第一要素。回应越慢，舆论就越被动。但速度不意味着草率——在事实不清的时候，可以先发布简短的初步回应，再逐步补充细节。

### 原则二：真诚

用真诚的态度面对问题，不回避、不推诿、不狡辩。用平实的语言说话，而不是冷冰冰的官方辞令。

### 原则三：担当

作为服务提供者，首先要承担起责任。即使问题的部分原因在于用户的操作或第三方的服务，也应该先承担起自己的责任，再说明具体的原因。

### 原则四：行动

光有态度不够，还要有行动。具体的补救措施、具体的改进计划、具体的时间节点，比任何漂亮的言辞都更有说服力。

### 原则五：一致

公司的所有对外渠道——官方声明、客服回复、员工的个人发言、高管的采访——要保持口径一致。口径不一致会让公众觉得公司在隐瞒什么。

### 中国企业危机公关的常见错误

以下是中国企业在危机公关中常见的错误，Agent 公司要坚决避免：

- **删帖控评**：试图删除负面信息或操控评论。在当今的舆论环境中，这几乎必然会被发现并引发更大的反弹。
- **甩锅临时工**：把责任推给"临时工""个别员工""外包人员"。公众已经对这种说辞非常反感。
- **律师函警告**：对批评者发律师函，试图用法律手段压制批评。除非确实是恶意的造谣诽谤，否则这种做法会让公司显得傲慢和霸道。
- **冷漠的官方回应**：用冷冰冰的官方语言回应，缺乏人情味和诚意。
- **避重就轻**：只回应次要的问题，回避核心的问题。
- **反复变化**：回应的口径反复变化，前后矛盾。

## 17.6 Agent 事故回应的特殊要点

Agent 事故（尤其是行为事故）的回应，除了遵循上述通用原则外，还有一些特殊要点。

### 要点一：解释 Agent 为何这样做

公众对 AI 的行为往往有很多误解和恐惧："AI 是不是失控了？""AI 是不是有自己的想法？"在回应 Agent 事故时，要尽可能清晰地解释 Agent 为什么会做出这样的行为：是对用户指令的误解？是权限配置的问题？是受到了外部内容的干扰？是某个已知的技术局限？

清晰的解释能够消除公众对"AI 失控"的恐惧，把问题定性为一个可以理解、可以解决的技术问题。

### 要点二：公布具体的技术改进

说明为了防止类似事故再次发生，你采取了哪些具体的技术改进措施。比如：

- 增加了哪些操作的确认步骤；
- 收紧了哪些默认权限；
- 增加了哪些检测和拦截机制；
- 改进了 Agent 在哪些情况下的判断逻辑。

具体的技术改进，比"我们会加强管理"之类的空话更有说服力。

### 要点三：不要把责任推给用户

在 Agent 事故中，有时候确实存在用户操作上的问题：用户给了过高的权限、用户的指令有歧义、用户没有审核 Agent 的结果。但在公开回应中，**不要把责任推给用户**。

"用户操作不当"这样的说法，即使在技术上有一定道理，也会让所有用户感到不安："如果我也'操作不当'，是不是也会出事？"更好的做法是：承认产品的设计应该能够防止这种情况的发生，并说明你将如何改进产品，让用户即使在操作不完美的情况下也能保持安全。

### 要点四：区分个案与系统性问题

明确说明这次事故是个案还是系统性问题。如果是个案，说明为什么它不会影响其他用户；如果是系统性问题，说明影响的范围和处理的计划。

## 17.7 回应声明的结构

一份好的危机回应声明，通常包括以下部分：

1. **事件说明**：简要、准确地说明发生了什么。
2. **致歉**：对受影响的用户真诚致歉。
3. **原因说明**：解释问题发生的原因（如果已经查明）。
4. **已采取的措施**：说明已经采取的处理和补救措施。
5. **后续计划**：说明后续的改进计划和时间表。
6. **用户支持**：告诉受影响的用户如何获得帮助和补偿。
7. **联系方式**：提供进一步沟通的渠道。

声明的语言要平实、真诚，避免过度的法律辞令和公关套话。篇幅要适中，太短显得敷衍，太长让人抓不住重点。

## 17.8 与监管部门的沟通

如果危机涉及合规问题，或者引起了监管部门的关注，需要妥善处理与监管部门的沟通：

- **主动报告**：对于数据安全事件等法规要求报告的事件，按照规定及时向监管部门报告。
- **积极配合**：配合监管部门的调查，如实提供信息。
- **认真整改**：按照监管部门的要求认真整改，并按时报告整改情况。
- **专业支持**：寻求专业律师的支持，确保应对措施合法合规。

在中国，监管部门的态度对企业的生存和发展有重大影响。积极配合、认真整改，是获得监管部门理解的基础。

## 17.9 危机后的信任重建

危机处理完毕，并不意味着危机的影响已经消除。用户和客户的信任受到了损伤，需要时间和努力来重建。

### 公开的事故复盘

一些优秀的技术公司有发布"事故复盘报告"的文化：在重大故障或事故之后，公开发布详细的复盘报告，说明事故的经过、原因、影响和改进措施。这种做法展示了公司的透明度和对问题的负责态度，往往能够赢得技术用户的尊重。

对于 Agent 公司来说，在重大事故之后发布公开的复盘报告，是重建信任的有效方式。报告应该做到：

- **诚实**：如实说明事故的经过和原因，不掩盖、不美化。
- **具体**：提供具体的时间线、技术细节、影响数据。
- **建设性**：重点说明从事故中学到了什么、做了哪些改进。

### 改进承诺的跟踪

在危机回应中做出的改进承诺，要认真落实，并在适当的时候公开进展。如果承诺了却没有兑现，会对信任造成二次伤害。

### 持续的信任建设

危机之后，要更加重视信任的建设：加强安全能力的宣传、发布安全报告、邀请第三方审计、加强与用户的沟通。

## 17.10 应对竞争攻击与谣言

在激烈的市场竞争中，有时会遇到竞争对手或其他利益相关方的恶意攻击：有组织的负面评论、断章取义的对比、毫无根据的谣言。

### 应对原则

- **保持冷静**：不要情绪化地回应，不要陷入口水战。
- **核实事实**：首先确认攻击的内容是否有事实依据。如果有部分事实，要正视问题。
- **用事实说话**：针对不实信息，用事实和证据进行澄清。
- **借助第三方**：邀请客户、合作伙伴、独立的第三方发声，比自己辩解更有说服力。
- **法律手段**：对于确实构成造谣诽谤、商业诋毁的行为，在证据充分的情况下，可以通过法律途径维护权益。
- **不以牙还牙**：不要用同样的方式攻击对手。这样做会损害自己的品牌，也可能违反反不正当竞争的相关规定。

## 17.11 案例：两种回应，两种结局

> 以下为虚构的对比案例，用于说明不同回应方式的效果。

假设一款编程智能体在某天发生了一起事故：一位开发者在使用 Agent 清理测试环境时，Agent 误将一个连接到共享数据库的配置识别为测试环境，执行了清理命令，导致该开发者所在团队的共享开发数据库被清空。虽然这不是生产数据库，但团队几天的开发数据丢失了。这位开发者在社交媒体上发布了事故截图和经过，很快在开发者社区中引发了广泛讨论。

### 回应方式 A：防御型

公司在事故发生一天后发布了一份简短的声明："经调查，该事故是由于用户授予了 Agent 过高的权限，并且没有在执行前审核 Agent 的操作计划导致的。我们的产品文档中已明确提示用户谨慎授予权限。我们建议用户遵循最佳实践，合理配置权限。"

**结果**：声明发布后，舆论迅速恶化。开发者们纷纷表示："所以出了事就是用户的错？""那我还敢用吗？"更多的用户开始分享自己遇到的类似问题。几个技术博主发布了"这款 Agent 的安全隐患"的分析视频。一周后，产品的新用户注册量明显下降，多家企业客户暂停了推广计划。

### 回应方式 B：担当型

公司在发现社交媒体上的讨论后，几个小时内就发布了初步回应："我们已经注意到这起事故，非常抱歉给这位开发者和他的团队带来了损失。我们的团队已经联系了这位开发者，正在协助他尝试恢复数据。我们正在全面调查事故原因，会在 24 小时内公布调查结果。"

第二天，公司发布了详细的调查说明：

"经过调查，事故的原因是：Agent 在判断目标环境时，主要依据配置文件的命名，而这个配置文件的命名包含'test'字样，但实际连接的是共享开发数据库。我们的产品在执行数据库清理这类高风险操作前，虽然会展示操作计划，但没有对'目标是否为共享资源'进行额外的检查和警示。这是我们产品设计上的不足。

我们已经采取了以下措施：
一、对所有涉及数据删除的操作，增加了强制的二次确认，并明确显示操作目标的详细信息；
二、Agent 在执行数据库操作前，会主动检查连接的数据库是否为共享资源，如果是，会给出醒目的警告；
三、我们更新了默认权限配置，数据库删除类操作默认需要用户确认。

我们为受影响的团队提供了技术支持，协助恢复了部分数据，并提供了服务补偿。我们也会在两周内发布一份完整的事故复盘报告。"

两周后，公司如期发布了完整的复盘报告，详细说明了事故的时间线、技术原因、改进措施，以及从这次事故中学到的经验。

**结果**：初步回应发布后，舆论开始缓和。很多开发者表示："态度很好""这才是负责任的公司"。详细的调查说明和改进措施发布后，讨论的焦点从"这款 Agent 不安全"转向了"Agent 安全设计应该怎么做"。复盘报告在技术社区获得了广泛的好评，有人评论说："这份报告比很多公司的产品文档都有价值。"一个月后，产品的新用户注册量恢复正常，部分企业客户表示，这次事故的处理方式反而增加了他们对公司的信任。

### 对比启示

1. **速度**：B 在几个小时内回应，A 一天后才回应。
2. **担当**：B 承认了产品设计上的不足，A 把责任推给了用户。
3. **解释**：B 清楚地解释了 Agent 为什么会做出错误的判断，A 没有解释。
4. **行动**：B 公布了具体的技术改进措施，A 只是建议用户遵循最佳实践。
5. **透明**：B 发布了完整的复盘报告，A 没有后续。
6. **结果**：B 把一次危机转化为展示负责任态度的机会，A 让危机进一步恶化。

## 本章要点

1. Agent 危机的独特性：自主行为带来新型事故、截图录屏传播迅速、AI 话题放大效应、"翻车"内容有流量、信任受损难以恢复。
2. 八种危机类型：能力翻车、行为事故、内容风险、数据安全事件、计费争议、舆论争议、合规事件、竞争攻击。
3. 预防：绘制风险地图；产品层面落实安全设计、红队测试、发布前检查、危险操作保护；营销层面做好期望管理、用语审查、计费透明；建立舆情监测、危机预案与演练。
4. 响应五步：确认事实、评估级别、首次回应、处理与补救、复盘与沟通。
5. 回应五原则：速度、真诚、担当、行动、一致。避免删帖控评、甩锅临时工、律师函警告、冷漠回应、避重就轻、反复变化。
6. Agent 事故回应的特殊要点：解释 Agent 为何这样做、公布具体技术改进、不要把责任推给用户、区分个案与系统性问题。
7. 涉及合规问题时，主动报告、积极配合、认真整改。
8. 危机后通过公开的事故复盘、改进承诺的跟踪、持续的信任建设来重建信任。
9. 应对竞争攻击要冷静、用事实说话、借助第三方，不以牙还牙。
