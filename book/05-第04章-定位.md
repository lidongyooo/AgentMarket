# 第二部分　定位篇：在"什么都能做"中找到立足点

---

# 第 4 章　定位：从"万能助手"到"一个岗位"

> 客户不会雇用一个"什么都能做"的人，客户会雇用一个"这件事交给他准没错"的人。

## 4.1 万能的诅咒

几乎每一个 Agent 创业团队，在产品诞生之初都会经历一个甜蜜而危险的时刻：团队发现自己的 Agent 似乎什么都能做。写代码可以，写报告可以，做表格可以，查资料可以，订机票似乎也可以。于是，官网上写着"你的全能 AI 助手"，发布会上演示了二十个场景，销售人员见到任何客户都说"这个我们也能做"。

然后，团队会发现一个奇怪的现象：**看过演示的人都说好，但真正用起来的人很少，长期用下去的人更少。**

这就是"万能的诅咒"。它的成因有三：

**第一，客户无法想象。**"什么都能做"等于没有告诉客户应该用它来做什么。客户的注意力是有限的，他需要一个具体的理由才会开始使用一个新工具。当你说"什么都能做"时，客户听到的是"你自己去想该用它做什么吧"。大多数客户不会花这个精力。

**第二，每个场景都不够好。**通用能力意味着在每个具体场景中，Agent 都只能做到"还可以"。而客户在具体场景中，总能找到一个做得更好的专门工具，或者干脆自己做。"还可以"在演示中够用，在日常工作中不够用。

**第三，信任无法积累。**信任需要在一个具体的任务上反复被验证才能建立。当客户今天用 Agent 写报告、明天用它查资料、后天用它做表格，每一次都是新的任务、新的风险，信任始终停留在起点。

破解"万能的诅咒"，需要做一件反直觉的事：**主动收窄**。把 Agent 从"什么都能做"收窄到"最擅长做某一件事"，先在这件事上做到让客户离不开，再逐步扩展。

这并不意味着你要阉割产品的能力。Claude 这样的通用模型产品依然可以是通用的，但它在营销中会反复强调几个代表性的高价值场景，比如编程、写作、分析与研究；Claude Code、Codex 则直接把编程这一个场景做到极致，成为品类代表。**能力可以是通用的，但定位必须是具体的。**

## 4.2 岗位定位法

我们推荐一种特别适合 Agent 的定位方法：**岗位定位法**。

它的核心思想是：既然 Agent 是"同事"而不是"工具"，那就像招聘一个员工一样来定义它。每一个员工都有一份岗位说明书，你的 Agent 也应该有一份。

### Agent 岗位说明书模板

| 项目 | 说明 | 示例（编程智能体） | 示例（财务对账智能体） |
|---|---|---|---|
| **岗位名称** | 用客户熟悉的语言命名 | 缺陷修复与测试补全工程师 | 供应商对账专员 |
| **服务对象** | 它为谁工作，向谁汇报 | 研发工程师、技术负责人 | 应付会计、财务经理 |
| **核心职责** | 三到五项具体工作 | 定位并修复缺陷；补全单元测试；按规范重构代码；撰写变更说明 | 读取各类格式对账单；与 ERP 应付数据逐笔比对；标出差异并说明原因；生成对账报告 |
| **不负责的事** | 明确的边界 | 不负责架构设计决策；不直接合并到主干 | 不负责付款审批；不修改 ERP 数据 |
| **能力要求** | 它擅长的技能 | 熟悉主流语言与框架；能读懂大型代码库；会运行测试并根据结果修正 | 能识别多种格式与扫描件；理解常见对账差异类型 |
| **工作权限** | 它能访问什么、能做什么 | 读写指定仓库；运行测试命令；创建分支与合并请求 | 只读 ERP 应付数据；读取指定邮箱附件；写入对账结果表 |
| **工作方式** | 自主程度与汇报机制 | 接到任务后自主执行，完成后提交合并请求等待人工评审 | 每日自动执行，差异项提交会计复核 |
| **考核指标** | 如何衡量它干得好不好 | 修复通过率、评审一次通过率、节省工时 | 差异识别准确率、对账周期、人工复核量 |
| **"薪酬"** | 它的成本 | 按席位加用量 | 按供应商数量阶梯计价 |

这份说明书有几个神奇的作用：

**对客户来说**，它把一个抽象的 AI 产品翻译成了一个可理解、可评估、可管理的"员工"。客户立刻知道它能干什么、不能干什么、怎么管它、怎么评价它、花多少钱。

**对销售来说**，它是一个现成的沟通框架。销售人员可以拿着这份说明书和客户讨论："您团队里现在谁在做这些事？每月花多少时间？如果交给它，您需要配合做什么？"

**对产品来说**，它迫使团队想清楚 Agent 的边界、权限和考核标准。很多 Agent 产品的体验问题，根源就在于这些问题没有被想清楚。

**对客户成功来说**，它是上岗后的"绩效考核表"，可以用来定期评估 Agent 的表现。

### "不负责的事"比"负责的事"更重要

在岗位说明书中，最容易被忽视、但最重要的一栏是"**不负责的事**"。

明确告诉客户 Agent 不做什么，看似会削弱产品的吸引力，实际上会大大增强信任。原因很简单：一个说自己什么都能做的人，你不敢信任；一个清楚说明自己边界的人，你会觉得他靠谱。

更重要的是，"不负责的事"往往对应着客户最担心的风险。"不直接合并到主干"回应了技术负责人对代码质量的担忧；"不修改 ERP 数据"回应了财务和信息安全对数据完整性的担忧；"不负责付款审批"回应了对资金安全的担忧。**边界就是安全感。**

## 4.3 任务地图：找到你的"黄金任务"

岗位定位法的前提是选对岗位。一个 Agent 应该定位于哪个岗位、承担哪些任务？我们用**任务地图**来回答这个问题。

### 四个筛选维度

对每一个候选任务，从四个维度打分（每项 1–5 分）：

1. **频次**：这个任务多久发生一次？每天都有的任务得 5 分，一年一次的任务得 1 分。高频任务意味着更多的使用机会、更快的习惯养成和更高的累积价值。
2. **价值**：这个任务由人来做需要多少成本？或者做好了能带来多少收益？耗时长、需要高技能人员的任务得分高。
3. **可验证性**：这个任务的结果是否容易判断对错？有明确标准答案、可以自动检查的任务得 5 分，完全依赖主观判断的任务得 1 分。
4. **容错度**：这个任务出错的后果有多严重？出错后容易发现、容易纠正、损失很小的任务得 5 分，出错可能造成重大损失且难以挽回的任务得 1 分。

此外还有一个"一票否决"维度：**Agent 当前的完成能力**。如果以 Agent 目前的能力，这个任务的完成率很低，那么无论其他维度多高，都不适合作为定位核心。

### 黄金任务的特征

四个维度都高分的任务，我们称之为**黄金任务**：高频、高价值、易验证、可容错。

黄金任务是 Agent 定位的最佳起点，因为在这些任务上：

- 客户能频繁使用 Agent，快速形成习惯；
- 每一次使用都能带来可感知的价值；
- 客户能轻松判断 Agent 干得好不好，信任可以快速积累；
- 即使 Agent 偶尔出错，后果也可以接受。

编程领域的缺陷修复、单元测试编写、代码评审辅助，财务领域的对账、发票核验，客服领域的常见问题回复，运营领域的数据日报，都是典型的黄金任务。

### 任务地图示例

下面是一个面向电商企业的 Agent 产品团队，在定位阶段绘制的任务地图（分数为示意）：

| 候选任务 | 频次 | 价值 | 可验证性 | 容错度 | 当前完成能力 | 总分 | 结论 |
|---|---|---|---|---|---|---|---|
| 商品详情页文案生成 | 5 | 3 | 3 | 4 | 高 | 15 | 可做，但竞争激烈 |
| 竞品价格监控日报 | 5 | 3 | 5 | 4 | 高 | 17 | **黄金任务** |
| 客服售前咨询回复 | 5 | 4 | 3 | 3 | 中高 | 15 | 可做，需人工兜底 |
| 订单异常处理 | 4 | 4 | 4 | 3 | 中 | 15 | 第二阶段 |
| 店铺运营策略分析 | 2 | 5 | 1 | 4 | 中 | 12 | 暂不作为核心 |
| 自动调价执行 | 4 | 5 | 4 | 1 | 中 | 14 | 风险高，暂缓 |
| 平台规则变更解读 | 2 | 3 | 3 | 4 | 高 | 12 | 作为附加价值 |

团队最终选择以"竞品价格与库存监控"作为核心定位，以"客服售前咨询"作为第二场景，把"自动调价"列为远期规划——在客户对 Agent 建立充分信任之后再开放。

### 从黄金任务到岗位

选出黄金任务后，把相关的任务组合在一起，就形成了一个"岗位"。一个好的岗位通常包含**一个核心黄金任务**和**两到四个相关的辅助任务**。核心任务负责建立信任和习惯，辅助任务负责扩大价值和提高黏性。

比如，上面的电商 Agent 最终的岗位定义是"电商竞争情报专员"：核心任务是竞品价格与库存监控，辅助任务包括竞品新品追踪、竞品促销活动汇总、每周竞争态势简报。

## 4.4 选择你的参照物

定位的本质是在客户心智中找到一个位置。而客户理解一个新事物，总是需要借助一个已知的参照物。Agent 定位时，有三种常见的参照物选择。

### 参照物一：对标人

"它就像一个初级程序员""它是你的 AI 财务专员""一个永不下班的客服"。

**优点**：最直观，客户一听就懂；方便客户用人力成本来衡量价值；契合"同事"的产品本质。

**缺点**：容易引发过高期望——客户会拿真人的标准来要求它，而 Agent 在某些方面（比如常识判断、跨部门沟通）可能远不如人；容易引发员工的替代焦虑；在某些场合可能被认为是在宣传"取代人工"，引发舆论争议。

**使用建议**：对标人时，尽量对标"初级岗位"或"助理岗位"，而不是"资深专家"；强调"协助"和"分担"，而不是"替代"；在说明书中明确它与真人的差异。

### 参照物二：对标工具

"比 RPA 更灵活""会自己干活的 Excel""能理解需求的自动化脚本"。

**优点**：在已有工具的认知基础上做升级，客户容易理解增量价值；不会引发替代焦虑；方便进入已有的预算科目。

**缺点**：可能让客户低估 Agent 的价值，把它当作一个"更好的工具"而不是"新同事"；容易陷入与原有工具的功能对比和价格对比。

**使用建议**：适合面向已经采购过相关工具的客户，或者在保守型组织中降低接受门槛。

### 参照物三：对标品类

"编程智能体""AI 对账平台""智能客服"。

**优点**：如果品类已经有了清晰的认知，可以直接借用品类认知，降低沟通成本；有利于搜索和比较；有利于成为品类代表。

**缺点**：品类认知可能被领先者定义，你只能做跟随者；如果品类认知还不清晰，你需要先教育品类。

**使用建议**：如果你有能力成为品类代表，就大胆地定义品类；如果品类已经有了强势的领先者，就在品类中找一个细分位置。

### 关于"数字员工"这个词

在中国市场，"数字员工"是一个非常流行的说法，很多 Agent 产品和 RPA 产品都使用这个词。它属于"对标人"的参照物，优点和缺点都很明显。

我们的建议是：**在面向企业管理层时可以使用"数字员工"**，因为管理层习惯从组织和人力的角度思考问题，"数字员工"有助于他们理解价值和规划组织变革；**在面向一线员工和开发者时，慎用"数字员工"**，可以改用"AI 助手""智能体""AI 搭档"等说法，避免引发抵触。开发者尤其反感过度拟人化的营销包装，对他们来说，"编程智能体""在终端里干活的 AI"这样直接描述产品形态的说法更有效。

## 4.5 差异化的五个来源

定位不仅是"我是什么"，还要回答"我和别人有什么不同"。在模型能力快速同质化的今天，Agent 产品的差异化从哪里来？我们总结了五个来源。

### 来源一：场景深度

对一个场景理解得越深，Agent 在这个场景中的完成率就越高。场景深度来自于：行业知识的积累、对业务流程细节的理解、针对场景的工具和数据接入、大量真实任务的打磨。

**营销表达**："我们只做一件事，并且做了 XX 万次。""我们的团队来自 XX 行业，比你更懂你的流程。"

### 来源二：交付形态

同样的能力，以不同的形态交付，会形成不同的价值。比如编程智能体，有的嵌入编辑器，有的运行在终端，有的在云端沙箱异步执行，有的部署在企业私有环境。不同形态适合不同的用户和场景。

**营销表达**："在你习惯的地方工作。""数据不出你的机房。""在钉钉里直接派活。"

### 来源三：生态集成

Agent 能连接的系统越多，能干的活就越多，客户的迁移成本也越高。在中国市场，与钉钉、飞书、企业微信、主流国产 ERP/CRM、国产数据库、国产操作系统、国内主流云平台的集成，都是重要的差异化来源。

**营销表达**："开箱支持 XX 个国内主流系统。""与你现有的系统无缝衔接。"

### 来源四：可控与信任

在 Agent 领域，"更可控"本身就是一种重要的差异化。细粒度的权限控制、完整的操作日志、可配置的审批节点、一键回滚、合规资质，这些都能让企业客户更放心。

**营销表达**："每一步都看得见、管得住、撤得回。"

### 来源五：服务与陪跑

在中国企业服务市场，服务能力往往是决定成败的关键。很多企业客户需要的不只是一个产品，而是一个能帮他们把 Agent 真正用起来的伙伴。驻场实施、流程梳理、员工培训、持续优化，这些服务能力难以被快速复制。

**营销表达**："不只是交付一个 Agent，而是陪你把它用起来。""上线不是结束，而是开始。"

### 一个重要的提醒：模型不是差异化

很多 Agent 产品喜欢把"我们使用了某某最强模型"作为卖点。在早期，这可能有一定吸引力；但在今天，这几乎不构成差异化，原因有三：

1. 强大的模型可以被所有人调用，你能用，竞争对手也能用；
2. 模型的领先地位变化极快，今天的最强可能几个月后就被超越；
3. 客户关心的是结果，而不是模型。

当然，如果你是一家模型公司，模型能力本身就是你的核心竞争力，应该大力宣传。但对于应用层的 Agent 公司来说，更好的策略是强调**"模型无关"**或**"多模型调度"**——"我们会为每个任务选择最合适的模型""模型升级，你的 Agent 自动变强"。这不仅避免了对单一模型的依赖，还能回应客户对供应商锁定和合规的顾虑——在中国市场，支持国产模型、支持私有化部署开源模型，往往是政企客户的硬性要求。

## 4.6 写好你的定位语句

经过上面的分析，现在可以写出你的定位语句了。我们推荐使用以下结构：

> **为【目标客户】，在【具体场景】中，【完成什么任务、交付什么结果】。与【主要替代方案】不同，我们【独特之处】。**

下面是几个示例：

**示例一：编程智能体**

> 为中大型企业的研发团队，在日常缺陷修复与测试补全工作中，自主定位问题、修改代码、运行测试并提交合并请求。与只能给出建议的编程助手不同，我们直接交付经过测试验证的代码变更，并支持私有化部署，代码不出企业内网。

**示例二：财务对账智能体**

> 为年采购额过亿的制造企业财务部门，在每月的供应商对账工作中，自动读取各种格式的对账单并与 ERP 比对，标出差异并说明原因。与传统 RPA 不同，我们能处理格式不统一的对账单和扫描件，供应商格式变化无需重新配置。

**示例三：电商竞争情报智能体**

> 为天猫、京东、抖音电商的中腰部品牌商家，每天自动监控竞品的价格、库存和促销活动，生成竞争态势日报。与人工盯店和通用爬虫工具不同，我们不仅给数据，还给出"竞品在做什么、你该怎么应对"的分析建议。

**示例四：面向开发者的 Agent 开发平台**

> 为需要在企业内部构建 AI 智能体的开发团队，提供从开发、调试、部署到运行监控的一站式平台。与只提供模型 API 的云服务不同，我们提供生产级的 Agent 运行环境、权限管控和可观测性，让 Agent 从演示走向生产。

定位语句是内部使用的战略工具，不需要直接出现在广告文案中。但所有的对外信息——官网首页、产品介绍、销售话术、广告文案——都应该从定位语句中提炼出来，确保一致。

### 从定位语句到一句话介绍

定位语句往往比较长，对外传播时需要提炼成一句话介绍（也就是常说的"slogan"或"一句话价值主张"）。提炼的原则是：**说结果，不说技术；说具体，不说宏大；说客户的语言，不说行业黑话。**

| 不好的一句话介绍 | 问题 | 更好的一句话介绍 |
|---|---|---|
| 基于大模型的下一代智能体平台 | 只说技术，没说结果 | 让你的研发团队每周多出一天 |
| 赋能企业数智化转型的 AI 引擎 | 空洞宏大，充满黑话 | 供应商对账，从三天缩短到半天 |
| 最强 AI 编程助手 | 绝对化用语，有法律风险，且无区分度 | 交代一句话，它把代码改好、测试跑通 |
| 你的全能 AI 员工 | 万能的诅咒 | 每天早上九点，竞品动态已在你的钉钉里 |

## 4.7 命名：品类词与产品名

### 品类词的选择

在中文语境中，Agent 相关的品类词有很多：智能体、AI 智能体、Agent、AI 助手、AI 助理、数字员工、AI 同事、Copilot、AI 搭档……这些词的心智含义不同：

- **智能体**：官方、中性、规范，政策文件和主流媒体普遍使用，适合面向政企和正式场合。
- **Agent**：技术圈和投资圈的通用说法，在开发者和科技从业者中认知度高，但对普通用户和传统行业客户有理解门槛。
- **AI 助手 / AI 助理**：亲和、易懂，但暗示被动和辅助，可能低估 Agent 的自主能力。
- **数字员工**：强调替代人力，适合面向管理层讲组织价值，但可能引发员工抵触。
- **Copilot（副驾驶）**：强调人机协作、人在主导，适合强调安全可控的场景，但这一说法与特定海外品牌关联较强。

建议根据目标客户选择主品类词，并在不同场合灵活切换。比如官网首页用"智能体"，开发者文档用"Agent"，面向一线员工的培训材料用"AI 助手"。

### 产品命名的原则

如果你正在为 Agent 产品命名，有几条在中国市场特别重要的原则：

1. **好读、好写、好搜**。中国用户主要通过搜索、口头推荐、社交媒体传播来了解产品。一个读不出来、写不对、搜不到的名字会严重影响传播效率。纯英文名在开发者群体中没问题，但面向更广泛的用户时，最好有一个好记的中文名。
2. **避免与大厂产品撞名**。在中国，大厂的产品线极其丰富，取名前要做充分的检索，避免与大厂产品名称相近，否则你的搜索流量会被大厂截走。
3. **提前注册商标和域名**。AI 行业的商标抢注现象比较普遍，产品名确定后应第一时间在相关类别注册商标，同时注册域名和主要社交平台账号。
4. **考虑拟人化程度**。给 Agent 起一个人名（比如"小 X"），能增加亲和力，但也会强化"对标人"的期望。面向 C 端和中小企业可以适度拟人化，面向开发者和技术决策者则应克制。

## 4.8 验证你的定位

定位不是在会议室里拍脑袋决定的，它需要经过验证。以下是四个简单有效的验证方法。

**方法一：五秒测试。**把官网首页或产品介绍给一个不了解产品的目标用户看五秒钟，然后拿走，问他："这个产品是做什么的？给谁用的？"如果他答不上来，或者答得和你的定位差很远，说明定位表达有问题。

**方法二：客户复述测试。**在与客户的沟通结束后，请客户用自己的话向同事介绍你的产品（或者在客户内部汇报材料中观察他是怎么描述你的产品的）。客户的复述，才是你的定位在客户心智中的真实样子。

**方法三：销售转述测试。**让三位销售人员分别向一个模拟客户介绍产品，比较他们的表述是否一致。如果每个销售讲的都不一样，说明定位没有在内部对齐。

**方法四：搜索词验证。**检查目标客户在搜索引擎、社交媒体、应用商店中实际使用什么词来寻找类似产品。如果你的定位用词和客户的搜索用词不匹配，即使定位再精准，客户也找不到你。

## 4.9 案例：从"全能 AI 程序员"到"遗留系统迁移专家"

> 以下为综合化、匿名化案例，公司名为化名，数字为示意。

"码途科技"是一家成立于 2024 年的编程智能体创业公司。产品最初的定位是"你的全能 AI 程序员"，宣传它能写新功能、修 bug、写测试、做代码评审、写文档、做重构……

产品上线后，团队在开发者社区做了大量推广，注册用户增长不错，但很快遇到了瓶颈：用户留存率低，付费转化率低，企业客户的销售周期很长且成单很少。更严重的是，在开发者社区里，越来越多的人把码途和大厂的免费编程工具相比较："功能差不多，人家还免费，为什么要用你的？"

团队做了一次深入的用户访谈，重点访谈了那些**持续使用并付费**的少数用户。他们发现了一个意外的规律：这些用户中，有相当比例的人在用码途做同一类事情——**把老旧的代码迁移到新的技术栈**。比如把老版本框架升级到新版本，把单体应用拆分成服务，把一种语言写的模块改写成另一种语言。

为什么这类用户特别喜欢码途？访谈揭示了原因：码途在早期为了处理大型代码库，专门做了一套"代码库理解与依赖分析"的能力，能够在修改之前先完整地梳理调用关系和影响范围。这个能力在日常的小修小补中体现不出优势，但在大规模迁移任务中价值巨大——迁移任务的核心难点恰恰是"改了这里，会不会影响那里"。

更重要的是，遗留系统迁移在中国企业中是一个巨大且持续的需求：大量企业有十几年前开发的老系统需要升级，信创替代带来了大规模的技术栈迁移需求，而熟悉老系统的工程师越来越少。迁移项目通常预算充足、周期明确、结果可验证（迁移后的系统能否通过原有的测试用例），完美契合黄金任务的特征。

码途决定重新定位：从"全能 AI 程序员"转为"**企业遗留系统迁移智能体**"。新的定位语句是：

> 为有老系统升级和技术栈迁移需求的中大型企业研发团队，自主梳理代码依赖、制定迁移方案、批量改写代码并通过回归测试验证。与通用编程助手不同，我们专为大规模、跨模块的迁移任务设计，每一处改动都能追溯影响范围。

重新定位后，码途做了一系列调整：官网首页只讲迁移场景；推出了"迁移评估"免费服务，帮助企业评估迁移工作量；与几家专注于信创改造的系统集成商建立了合作；在技术社区发布了一系列关于大规模代码迁移的深度技术文章。

半年后，码途的注册用户增长放缓了，但付费客户数和平均客单价都显著提升，企业客户的成交周期也明显缩短。更重要的是，在开发者社区里，人们开始说："如果要做迁移，可以试试码途。"——码途终于在客户心智中拥有了一个属于自己的位置。

### 案例启示

1. **最好的定位线索藏在你最忠实的用户身上。**不要只看平均数据，要深入研究那些持续使用并付费的用户，他们在用你的产品做什么。
2. **你的独特能力可能在通用场景中被埋没，在特定场景中才能闪光。**
3. **收窄定位会减少用户数量，但会提高用户质量。**对于 Agent 产品来说，后者更重要。
4. **好的定位能打开渠道。**清晰的定位让码途找到了天然的合作伙伴——信创改造集成商。

## 本章要点

1. "万能的诅咒"：Agent 什么都能做，客户反而不知道用它做什么。能力可以是通用的，但定位必须是具体的。
2. 岗位定位法：像招聘员工一样，为 Agent 写一份岗位说明书，包括岗位名称、服务对象、核心职责、不负责的事、能力要求、工作权限、工作方式、考核指标和"薪酬"。"不负责的事"比"负责的事"更能建立信任。
3. 任务地图：从频次、价值、可验证性、容错度四个维度为候选任务打分，找到高频、高价值、易验证、可容错的黄金任务。
4. 定位的参照物有对标人、对标工具、对标品类三种，各有利弊。"数字员工"适合面向管理层，慎用于一线员工和开发者。
5. 差异化的五个来源：场景深度、交付形态、生态集成、可控与信任、服务与陪跑。模型本身通常不是应用层产品的差异化来源。
6. 定位语句结构：为【目标客户】，在【具体场景】中，【完成什么任务】。与【替代方案】不同，我们【独特之处】。
7. 通过五秒测试、客户复述测试、销售转述测试、搜索词验证四种方法验证定位。
