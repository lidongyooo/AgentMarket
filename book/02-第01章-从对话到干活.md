# 第一部分　认知篇：看清"会干活的 AI"这门生意

# 第 1 章　从对话到干活：重新理解 AI Agent 这种产品

> 营销的第一步，是比客户更懂你卖的东西是什么。对于 Agent 来说，这一步比想象中更难。

## 1.1 一个周一早晨的两种工作方式

先看一个场景。

周一早上九点半，杭州某电商 SaaS 公司的后端工程师小林打开电脑。上周五下班前，测试同学在缺陷系统里给他提了七个问题：三个是接口返回格式不一致，两个是边界条件导致的空指针，一个是分页参数在某些情况下失效，还有一个是一段老代码里的时区处理错误。十点钟他还要参加一个一小时的需求评审会。

**第一种工作方式**是小林过去五年一直在用的：打开缺陷单，逐个定位代码，改，跑本地测试，提交，等代码评审。顺利的话，七个问题需要他一整天，会议还会把他的思路打断一次。中途他会打开一个聊天式 AI 助手，把报错信息粘贴进去，问"这是什么原因"，助手给出一段解释和一段示例代码，他再手动改到自己的项目里。

**第二种工作方式**是小林所在团队这个季度开始试点的：他在终端里打开一个编程智能体，把七个缺陷单的链接交给它，附上一句话："按缺陷单逐个修复，每个修复单独提交，修改后运行相关单元测试，测试不通过就继续改，搞不定的标记出来告诉我原因。"然后他去开会了。

一小时后会议结束，小林回到工位。智能体已经完成了五个修复，每个都附有修改说明和测试结果；时区问题它给出了两种修复方案并说明了各自的风险，等小林拍板；分页问题它判断需要改动一个公共组件，影响面较大，所以只写了分析报告，没有擅自修改。小林花了二十分钟逐个审阅，合并了五个修复，选定了时区方案，然后自己处理分页问题。上午十一点半，七个问题处理完毕。

这两种工作方式的差别，就是"对话式 AI"和"智能体 AI"的差别。

在第一种方式里，AI 是一个**顾问**：你问，它答，干活的还是你。在第二种方式里，AI 是一个**执行者**：你交代，它去做，你负责验收和拍板。

这个差别看似只是程度上的不同，实际上却是本质上的不同。它改变了价值的计量方式——顾问的价值以"回答质量"计，执行者的价值以"完成的工作量"计；它改变了人的角色——小林从"干活的人"变成了"派活和验收的人"；它也改变了风险的分布——顾问说错了，人还有机会判断；执行者做错了，错误可能已经写进了代码库。

营销 Agent，就是营销这种本质差别。

## 1.2 营销人需要懂的最小技术常识

很多营销人对 Agent 的技术细节望而却步，觉得那是工程师的事。这是一个危险的误区。Agent 是一个"能力边界"非常模糊的产品，如果营销人不理解它的基本工作原理，就很容易过度承诺，或者错失真正的卖点。

你不需要会写代码，但你需要理解下面这个最小模型。

### 一个 Agent 由五个部分组成

**1. 大脑：大语言模型。**这是 Agent 的推理核心，负责理解任务、制定计划、决定下一步做什么。模型的能力越强，Agent 能处理的任务越复杂、越模糊。Claude、GPT 系列以及国内的各类大模型，扮演的都是这个角色。

**2. 双手：工具。**模型本身只能输出文字，要真正"干活"，就必须调用工具：读写文件、执行命令、搜索网页、调用接口、操作浏览器、查询数据库、发送消息。工具决定了 Agent 能触达的范围。一个只能搜索网页的 Agent 和一个能直接修改生产数据库的 Agent，是完全不同风险等级的产品。

**3. 记忆：上下文与持久化存储。**Agent 需要记住任务目标、已经做过什么、环境是什么样的、用户有什么偏好。短期记忆主要依靠模型的上下文窗口，长期记忆则依靠外部存储、项目说明文件、知识库等机制。

**4. 规划：任务拆解与循环。**Agent 的核心工作方式是一个循环：**理解目标 → 制定计划 → 采取行动 → 观察结果 → 调整计划 → 再次行动**，直到任务完成或判断无法完成。这个循环可能跑几次，也可能跑几百次。

**5. 环境：Agent 工作的地方。**它可能是一台开发者的电脑终端，可能是云端的一个隔离沙箱，可能是企业的业务系统，也可能是一个浏览器。环境决定了 Agent 的权限边界，也决定了出错时的影响范围。

用一个比喻来概括：**模型是大脑，工具是双手，记忆是笔记本，规划是工作方法，环境是工位。**一个新员工能不能干好活，取决于他够不够聪明、手里有没有趁手的工具、有没有记录工作的习惯、做事有没有章法、以及工位上给他开了多少权限。Agent 也一样。

### 两个必须理解的关键概念

**第一个概念：自主程度。**不同的 Agent 自主程度差别很大。有的 Agent 每一步都要请示用户，有的 Agent 可以连续工作很长时间不打扰用户。自主程度越高，节省的人力越多，但风险也越大。很多 Agent 产品会提供不同档位的权限模式，让用户自己决定"放手"的程度。在营销中，自主程度是一个需要精心拿捏的卖点：对个人开发者，你可以强调"它能连续干很久不打扰你"；对企业安全负责人，你要强调"每一步都可以设置审批"。

**第二个概念：协议与生态。**Agent 要调用工具，就需要有标准的连接方式。2024 年底 Anthropic 提出并开源了模型上下文协议（Model Context Protocol，简称 MCP），试图为模型连接外部工具和数据源提供一个通用标准，此后得到了业界的广泛跟进，国内不少平台和工具也陆续提供了支持。类似的标准化努力还有很多。对营销人来说，理解协议的意义在于：**生态的开放程度会成为 Agent 产品的重要卖点**。客户会问："你能连接我们现有的系统吗？"一个支持主流协议、拥有丰富连接器的 Agent，回答这个问题会轻松得多。

## 1.3 Agent 与相邻品类的区别

客户在第一次接触 Agent 时，几乎一定会拿它和自己熟悉的东西做类比："这不就是一个更聪明的聊天机器人吗？""这和 RPA 有什么区别？""我们已经买了很多 SaaS 了，为什么还要买这个？"

营销人必须能够清晰、简洁地回答这些问题。下表是一个可以直接使用的对比框架。

| 维度 | 聊天式 AI 助手 | 传统 SaaS | RPA（流程自动化） | AI Agent |
|---|---|---|---|---|
| 交互方式 | 一问一答 | 人操作界面 | 预先录制脚本 | 交代目标，自主执行 |
| 谁来干活 | 人 | 人 | 机器按固定规则 | 机器按目标灵活决策 |
| 处理变化 | 依赖人转述 | 依赖人操作 | 流程一变就失效 | 能适应一定程度的变化 |
| 价值计量 | 回答质量 | 功能与效率 | 节省的重复操作 | 完成的工作量与结果 |
| 主要风险 | 回答错误 | 使用门槛 | 脚本脆弱 | 自主行为失控、越权 |
| 定价习惯 | 订阅 | 按席位订阅 | 按机器人数量 | 按用量、任务或结果，多为混合 |
| 用户角色 | 提问者 | 操作者 | 配置者 | 管理者与验收者 |

这张表里最值得营销人反复咀嚼的是最后一行：**用户角色**。

使用聊天助手的人是"提问者"，使用 SaaS 的人是"操作者"，而使用 Agent 的人是"管理者"。这意味着 Agent 的用户需要具备一种新的能力——**管理 AI 的能力**：清晰地描述任务、设定边界、检查结果、给出反馈。很多 Agent 产品在推广中遇到的阻力，本质上不是产品不够好，而是用户还没有学会当"管理者"。

所以，Agent 营销有一个隐藏任务：**培养用户成为合格的 AI 管理者**。这也解释了为什么在 Agent 领域，教程、最佳实践、提示词模板、工作流分享这些内容的营销价值会如此之高。

### 关于 RPA 的特别说明

在中国企业服务市场，RPA 有相当的认知基础，不少企业在过去几年采购过 RPA 产品。这对 Agent 营销来说既是机会也是挑战。

机会在于：这些企业已经有了"让机器替人干重复工作"的心智，预算科目也已经存在。挑战在于：部分企业对 RPA 的体验并不好——流程一变脚本就失效、维护成本高、实际节省的人力不如预期。他们可能会把 Agent 当作"又一个会失望的自动化项目"。

应对的方法是，**不要把 Agent 定位成"更好的 RPA"，而要定位成"能处理 RPA 处理不了的那部分工作"**。RPA 擅长的是规则明确、界面稳定的重复操作；Agent 擅长的是需要理解、判断、处理非结构化信息的工作。两者可以互补：RPA 负责确定性的部分，Agent 负责不确定性的部分。这种"互补"叙事，比"替代"叙事更容易让已经投入过 RPA 的客户接受。

## 1.4 Agent 产品的四种形态

"Agent"这个词今天被用得非常宽泛，几乎所有 AI 产品都会说自己是 Agent。为了让营销讨论更聚焦，我们把市场上的 Agent 产品大致分为四种形态。

### 形态一：通用助理型

这类产品面向个人用户，试图成为"什么都能帮你做"的全能助理。典型特征是：以对话为入口，能够联网搜索、读写文档、生成报告、制作表格和演示文稿、操作浏览器，甚至在云端虚拟环境里完成多步骤任务。Claude 的桌面与网页产品、ChatGPT 的智能体模式，以及 2025 年在国内引发广泛讨论的 Manus 等通用智能体，都属于这一形态的代表。国内各大厂的 AI 助手产品，也在不断向这一方向演进。

**营销特点**：用户规模大，传播性强，但用户对价格敏感，留存依赖于能否形成高频使用习惯。爆款演示容易出圈，但也容易引发"期望过高—体验落差"的反噬。

### 形态二：编程型

这类产品面向开发者，帮助编写、修改、测试、审查代码，甚至独立完成整个开发任务。Anthropic 的 Claude Code、OpenAI 的 Codex，以及 Cursor 等 AI 编程工具都是代表；国内也有阿里的通义灵码、字节的 Trae、腾讯的 CodeBuddy、百度的文心快码、智谱的 CodeGeeX 等产品。编程型 Agent 的形态也很丰富：有的嵌在编辑器里，有的运行在命令行终端里，有的在云端沙箱里异步执行任务并直接提交代码合并请求。

**营销特点**：用户专业度高，口碑传播极强，付费意愿相对较高，是目前商业化跑得最快的 Agent 品类。但开发者对营销话术极度反感，只认真实效果。

### 形态三：业务流程型

这类产品嵌入企业的具体业务流程，承担某个岗位或某类工作：客服智能体、销售线索跟进智能体、财务对账智能体、合同审查智能体、招聘筛选智能体、数据分析智能体、运维智能体等。它们通常需要接入企业的内部系统和数据，与企业的权限体系、审批流程深度集成。

**营销特点**：客单价高，决策链长，需要行业知识和交付能力，强依赖标杆案例。在中国市场，这类产品经常以"解决方案"或"项目"的方式交付。

### 形态四：平台型

这类产品不直接干活，而是帮助别人搭建 Agent：智能体开发平台、低代码 Agent 编排工具、Agent 运行与管理平台、Agent 开发框架与 SDK。国内的字节扣子（Coze）、阿里云百炼、百度千帆、腾讯元器等平台，以及海外的各类 Agent SDK 与开发框架都属于这一类。Anthropic 推出的 Claude Agent SDK，本质上也是把构建编程智能体的底层能力开放给开发者，去构建自己的 Agent。

**营销特点**：营销对象是"建造者"——开发者、企业 IT 团队、ISV（独立软件开发商）。核心卖点是生态、灵活性、成本与稳定性。平台型产品的营销往往和开发者生态建设高度重叠。

### 四种形态的营销重心对比

| 形态 | 核心客户 | 核心卖点 | 主要渠道 | 最大营销风险 |
|---|---|---|---|---|
| 通用助理型 | 个人用户、白领 | 省时、全能、惊艳 | 社交媒体、内容平台、应用商店 | 期望管理失败、留存差 |
| 编程型 | 开发者、技术团队 | 效率、质量、可控 | 开发者社区、口碑、开源 | 开发者反感营销、竞品替换成本低 |
| 业务流程型 | 企业业务部门 | 降本、提效、合规 | 直销、渠道、行业会议 | 交付失败、案例不可复制 |
| 平台型 | 开发者、企业 IT、ISV | 生态、灵活、成本 | 开发者大会、云市场、伙伴 | 生态冷启动、被大厂挤压 |

当然，现实中的产品往往跨越多种形态。比如一个编程型 Agent 也可能开放 SDK 成为平台，一个通用助理也可能推出企业版进入业务流程。但在制定营销策略时，**你必须明确自己的主形态**，因为不同形态的营销方法差异巨大，资源投入不能平均分配。

## 1.5 为什么编程智能体最先跑出来：可验证性原理

观察过去两三年 Agent 行业的发展，有一个现象非常值得营销人深思：**在各类 Agent 产品中，编程智能体是商业化最早跑通的品类之一，用户付费意愿和口碑传播都相当突出。**无论是海外的 Claude Code、Codex、Cursor，还是国内的各类 AI 编程工具，都在开发者群体中形成了真实的使用习惯和付费习惯。

为什么是编程？很多人会说"因为开发者最早接触 AI"或者"因为代码数据最多"。这些都是原因，但不是最根本的原因。最根本的原因是：

> **代码是一种结果可验证的工作。**

一段代码写得对不对，可以编译，可以运行，可以跑测试，可以让同事评审。Agent 写完代码，可以自己运行测试，看到失败就自己修改，直到测试通过。这种"行动—验证—修正"的闭环，让 Agent 能够在没有人类实时监督的情况下自我纠错，也让用户能够以很低的成本检验 Agent 的工作成果。

我们把这个规律称为**可验证性原理**：

> **一项工作的结果越容易被验证，Agent 在这项工作上越容易被信任，也就越容易被卖出去。**

可验证性原理对营销有三个直接的启示。

**启示一：选择可验证的场景作为切入点。**如果你的 Agent 要进入一个新行业，优先选择那些结果容易验证的任务。比如在财务领域，"对账"比"财务分析"更容易验证——对账结果平不平一目了然，而分析报告写得好不好见仁见智。先在可验证的任务上建立信任，再逐步扩展到难以验证的任务。

**启示二：为不可验证的工作"制造"验证机制。**很多有价值的工作天然不好验证，比如市场调研报告、营销文案、战略分析。这时候，产品和营销要一起想办法"制造"验证机制：引用来源可点击核查、关键数据可追溯、多方案对比让用户选择、提供置信度说明、设置人工抽检流程。验证机制本身就是卖点。

**启示三：把验证过程变成营销素材。**编程智能体的演示之所以有说服力，是因为观众可以看到测试从红变绿的过程。你的 Agent 也应该把"自我检查"的过程展示出来：它是如何发现自己的错误、如何修正、如何确认结果正确的。在营销素材中，"它是怎么检查自己的"往往比"它做出了什么"更能打动理性的客户。

## 1.6 Agent 营销的五个根本差异

理解了 Agent 是什么，我们就可以总结 Agent 营销与传统软件营销的根本差异了。这五个差异会贯穿全书，后面的章节都会在不同的维度上反复展开。

### 差异一：卖结果，而不是卖功能

传统软件营销的核心素材是功能清单："支持 XX 格式""集成 XX 系统""提供 XX 报表"。Agent 营销的核心素材是结果清单："完成了多少任务""替代了多少小时""交付了什么成果"。

一个常见的错误是把模型能力当作产品功能来宣传："支持百万级上下文""工具调用准确率达到 XX%""在某某基准测试中排名第一"。这些信息对技术决策者有一定参考价值，但对大多数客户来说，它们和"这件事能不能帮我干完"之间隔着太远的距离。

### 差异二：演示胜于说明

Agent 的价值很难用文字描述清楚，但很容易用演示呈现。一段三分钟的录屏，展示 Agent 从接到任务到交付成果的全过程，往往胜过一万字的产品说明。在中国的内容生态里，短视频和直播尤其适合呈现这种"过程感"。

但演示也有陷阱：精心挑选的成功案例可能制造过高的期望。我们会在第 8 章详细讨论如何做"诚实的演示"。

### 差异三：信任是第一门槛

客户对 Agent 的第一个疑问通常不是"它能做什么"，而是"它会不会搞砸""它会不会乱来""我的数据安全吗"。在传统软件营销中，安全与合规通常放在销售后期由技术团队回答；在 Agent 营销中，它们必须前置到营销的第一触点。

### 差异四：成本结构不同

传统软件的边际成本接近于零，多一个用户几乎不增加成本。Agent 的每一次运行都在消耗算力，复杂任务的成本可能相当可观。这意味着 Agent 产品的免费策略、定价策略、促销策略都必须重新设计。"免费无限用"在 Agent 领域往往是一条通往亏损的捷径。

### 差异五：用户需要被培养成"管理者"

前面已经提到，Agent 的用户是"管理者"而不是"操作者"。一个不会描述任务、不会设定边界、不会检查结果的用户，用任何 Agent 都会失望。因此，Agent 营销的很大一部分工作是**用户教育**——不是教用户点哪个按钮，而是教用户如何与 AI 协作。

## 1.7 一个贯穿全书的公式：净交付价值

为了让 Agent 的价值能被量化讨论，本书引入一个简单的公式，我们称之为**净交付价值**（Net Delivered Value，简称 NDV）：

> **净交付价值 = 任务价值 × 完成率 × 频次 − 监督成本 − 风险成本 − 使用成本**

逐项解释：

- **任务价值**：这项任务如果由人来完成，值多少钱。可以用人工时薪乘以耗时来估算，也可以用任务带来的业务收益来估算。
- **完成率**：Agent 独立完成任务、达到可接受质量的比例。完成率 90% 和完成率 50% 的 Agent，价值天差地别。
- **频次**：这项任务在一定时间内发生多少次。高频任务的价值会被放大。
- **监督成本**：人类为了让 Agent 完成任务而付出的时间——描述任务、检查结果、纠正错误、补完未完成的部分。这是最容易被忽视、也最容易让客户失望的成本。
- **风险成本**：Agent 出错可能造成的损失乘以出错概率。在低风险任务中可以忽略，在高风险任务中可能决定成败。
- **使用成本**：Agent 本身的费用，包括订阅费、用量费、部署和集成成本。

这个公式对营销的意义在于，它告诉我们**提升 Agent 价值的五个杠杆**：

1. **选择高价值任务**（提升任务价值）——定位问题，见第 4 章。
2. **选择 Agent 擅长的任务**（提升完成率）——场景选择问题，见第 4 章和第 11 章。
3. **选择高频任务**（提升频次）——留存与习惯问题，见第 10 章和第 15 章。
4. **降低用户的监督负担**（降低监督成本）——产品体验与用户教育问题，见第 10 章和第 15 章。
5. **建立安全与可控机制**（降低风险成本）——信任问题，见第 6 章。

而使用成本，则是定价问题，见第 5 章。

请特别注意**监督成本**。很多 Agent 产品在演示时看起来很惊艳，但客户真正用起来之后发现：描述任务要花很多时间，检查结果要花很多时间，纠正错误要花更多时间。算下来，还不如自己干。这种体验一旦形成，就会通过口碑迅速扩散。

所以，一个好的 Agent 营销故事，不仅要讲"它能做什么"，还要讲"你需要为它付出多少注意力"。"交代一句话，二十分钟后来验收"这样的表述之所以有力量，正是因为它同时传达了高完成率和低监督成本。

### 用净交付价值做一次快速自检

我们可以用小林的例子来算一笔粗账（数字为示意）：

- 任务价值：修复七个缺陷，人工需要约 6 小时，按工程师综合人力成本每小时 150 元计算，约 900 元。
- 完成率：智能体独立完成了 5 个，另外 2 个提供了有效分析，按约 80% 计。
- 频次：类似的缺陷修复工作每周约 3 次。
- 监督成本：小林审阅花了 20 分钟，自己处理剩余问题花了约 1 小时，合计约 1.3 小时，约 200 元。
- 风险成本：有测试和代码评审兜底，出错影响较小，暂计为很低。
- 使用成本：按团队订阅和用量折算，每次约几十元。

每次的净交付价值约为 900 × 80% − 200 − 少量风险成本 − 几十元 ≈ 400 多元，每周三次，每月就是数千元。对于一个工程师来说，这是一个清晰可感的价值。

当你能为自己的 Agent 算出这样一笔账，并且这笔账经得起客户推敲时，你的营销就有了坚实的地基。

## 1.8 营销人的 Agent 素养清单

最后，我们为营销团队列一份"Agent 素养清单"。在开始任何营销动作之前，团队里负责对外表达的每一个人都应该能回答这些问题：

1. 我们的 Agent 用的是什么模型？是否支持切换模型？模型来源是否会影响某些客户的采购决策？
2. 我们的 Agent 能调用哪些工具？能访问哪些数据？权限边界在哪里？
3. 我们的 Agent 在哪里运行？用户本地、我们的云端、还是客户的私有环境？
4. 我们的 Agent 有哪些自主程度档位？用户如何控制它的行为？
5. 我们的 Agent 最擅长的三类任务是什么？完成率大概是多少？
6. 我们的 Agent 最不擅长、最容易出错的三类任务是什么？
7. 我们的 Agent 如何检查自己的工作？用户如何验证结果？
8. 我们的 Agent 出错时会发生什么？能否回滚？
9. 一个典型任务的运行成本大概是多少？
10. 用户的数据会被如何使用？是否会用于模型训练？存储在哪里？

如果团队中有人回答不上来，就先别急着做营销。去找产品和技术团队，把这些问题弄清楚。**对产品的诚实理解，是 Agent 营销最重要的基本功。**

## 本章要点

1. Agent 与对话式 AI 的本质区别在于：前者是执行者，后者是顾问。Agent 营销的核心是说服用户"托付"一件事，而不仅仅是"使用"一个工具。
2. Agent 由模型、工具、记忆、规划和环境五部分组成。营销人需要理解这个最小模型，才能避免过度承诺。
3. 市场上的 Agent 产品大致可分为通用助理型、编程型、业务流程型和平台型四种形态，营销方法差异巨大，必须明确主形态。
4. 可验证性原理：结果越容易验证的工作，Agent 越容易被信任和购买。编程智能体最先跑通，根本原因在于代码可验证。
5. Agent 营销与传统软件营销有五个根本差异：卖结果、重演示、信任前置、成本结构不同、需要培养用户成为管理者。
6. 净交付价值 = 任务价值 × 完成率 × 频次 − 监督成本 − 风险成本 − 使用成本。这个公式揭示了提升 Agent 价值的五个杠杆。
