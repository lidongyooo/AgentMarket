# 第 11 章　企业销售：从 POC 到规模化上岗

> 传统软件的成交在签约那一刻，Agent 的成交在它稳定干活的那一天。

## 11.1 Agent 企业销售有什么不同

把 Agent 卖给企业，和把传统软件卖给企业，表面上看流程相似：找线索、做拜访、做演示、做方案、谈价格、签合同。但实际上，两者在本质上有很大的不同。

**传统软件卖的是"工具"**。客户买了工具，怎么用、用得好不好，主要是客户自己的事。供应商的责任是提供一个功能完整、稳定可靠的工具，以及必要的培训和支持。

**Agent 卖的是"上岗"**。客户买 Agent，是希望它能在自己的业务中承担一部分工作。而 Agent 能否真正上岗，取决于很多因素：能否接入客户的数据和系统、能否适应客户的业务流程、能否达到客户可接受的完成率、员工能否学会与它协作。这些因素中的任何一个出了问题，Agent 都无法上岗，客户的投入就打了水漂。

所以，Agent 企业销售的终点不是签约，而是**上岗**。这个认知会改变整个销售过程的设计：

- **销售前期**要做更深入的诊断，确保选对场景，而不是"客户要什么就答应什么"。
- **试点阶段**要像做项目一样认真管理，确保在真实环境中证明价值。
- **签约阶段**要把上岗所需的条件写清楚，包括双方的责任和配合事项。
- **签约之后**要持续投入，确保从试点走向规模化。

### Agent 销售团队的构成

正因为 Agent 销售的终点是上岗，Agent 企业销售团队的构成也与传统软件有所不同。一个典型的 Agent 销售团队通常包括四种角色：

**客户经理**：负责客户关系、商机推进、商务谈判。与传统软件的销售人员类似，但需要更强的业务理解能力，能够和客户讨论"哪些工作适合交给 Agent"。

**解决方案架构师**：负责技术方案设计、演示、技术答疑、安全评审支持。需要同时懂 Agent 技术和客户的业务与 IT 环境。

**前线部署工程师**：负责在客户现场把 Agent 真正部署起来、调通、优化。这是 Agent 时代越来越重要的一个角色——一些海外的 AI 公司专门设立了"前线部署工程师"（Forward Deployed Engineer）的岗位，派工程师深入客户现场，把产品能力转化为客户的业务价值。在中国，这类工作常常由实施顾问或交付工程师承担。

**客户成功经理**：负责签约后的持续服务，推动 Agent 从试点走向规模化，确保续约和扩张。

这四种角色需要紧密协作，形成一个"铁三角"甚至"铁四角"。很多 Agent 公司的教训是：销售人员单兵作战，签下了合同，但交付团队跟不上，Agent 无法上岗，最终导致项目失败、客户流失、口碑受损。

## 11.2 线索从哪里来

Agent 企业销售的线索来源主要有以下几种：

1. **内容营销**：白皮书下载、网络研讨会报名、案例阅读等内容营销活动带来的线索（见第 8 章）。
2. **自下而上的信号**：个人用户或团队用户中出现的企业采购信号（见第 7 章）。
3. **活动与会议**：行业峰会、展会、闭门会、沙龙等线下活动中获取的线索。
4. **渠道伙伴**：云厂商、系统集成商、ISV 等合作伙伴推荐的线索（见第 13 章）。
5. **老客户推荐**：满意的客户向同行推荐。在中国企业服务市场，这往往是质量最高的线索来源。
6. **高层关系**：创始人、高管的个人关系网络。
7. **主动外呼与拜访**：销售人员主动开发的目标客户。

不同来源的线索质量和转化周期差异很大。一般来说，老客户推荐和自下而上信号的线索质量最高，因为客户已经有了信任基础或使用体验；主动外呼的线索质量最低，但可以覆盖更多的目标客户。

## 11.3 诊断：在销售之前先做"体检"

### 为什么诊断特别重要

Agent 项目失败的一个常见原因是：**一开始就选错了场景**。客户提出的需求可能并不适合 Agent，或者以当前的技术能力难以实现，或者数据条件不具备，或者没有明确的业务负责人。如果销售人员为了签单而照单全收，最终的结果往往是项目失败。

因此，Agent 企业销售的第一步不是推销，而是**诊断**——像医生一样，先了解客户的情况，再判断 Agent 是否适合、适合哪个场景。

### 诊断问题清单

以下是一份诊断问题清单，可以在与客户的前几次沟通中使用：

**关于任务**：
- 您希望 Agent 帮助完成哪些具体的工作？
- 这些工作目前由谁来做？有多少人？每周花多少时间？
- 这些工作的结果如何判断好坏？有没有明确的标准？
- 如果这些工作出了错，后果是什么？

**关于现状**：
- 目前完成这些工作的流程是什么样的？
- 目前的主要痛点是什么？是效率、质量、成本还是人手不足？
- 之前有没有尝试过用其他方式（比如 RPA、外包、其他 AI 工具）来解决？效果如何？

**关于数据与系统**：
- 完成这些工作需要用到哪些数据？这些数据存在哪里？
- 需要接入哪些业务系统？这些系统是否有开放的接口？
- 数据的质量如何？是否结构化？是否有大量的扫描件、手写件？
- 数据安全和合规方面有什么要求？是否需要私有化部署？

**关于组织**：
- 这个项目由谁来牵头？业务部门还是 IT 部门？
- 谁是最终的决策者？还需要哪些部门参与评审？
- 一线员工对 AI 的态度如何？
- 公司领导层对 AI 的重视程度如何？

**关于预算与时间**：
- 这个项目是否已经有预算？预算大概在什么范围？
- 预算的审批流程是什么样的？
- 您希望在什么时间看到效果？

### Agent 适配度评估

根据诊断的结果，可以用一个简单的评估表来判断客户需求与 Agent 的适配度：

| 评估维度 | 高适配 | 中适配 | 低适配 |
|---|---|---|---|
| 任务特征 | 高频、规则相对清晰、结果可验证 | 中频、需要一定判断 | 低频、高度依赖经验和主观判断 |
| 数据条件 | 数据可获取、质量较好 | 数据部分可获取，需要整理 | 数据难以获取或质量很差 |
| 系统条件 | 系统有开放接口 | 需要一定的集成开发 | 系统封闭，难以集成 |
| 风险容忍 | 出错后果可控，有人工复核环节 | 出错有一定影响，需要较强的控制 | 出错后果严重，难以挽回 |
| 业务负责人 | 有明确的、积极的业务负责人 | 有负责人但投入有限 | 没有明确的业务负责人 |
| 领导支持 | 高层明确支持 | 中层支持 | 没有领导支持 |
| 预算 | 已有预算 | 预算待申请 | 没有预算 |

如果多数维度为低适配，就应该坦诚地告诉客户：目前这个场景可能不太适合，或者需要先解决某些前提条件。**拒绝一个不适合的项目，比接下一个注定失败的项目更有价值。**这种坦诚还能赢得客户的尊重，为未来的合作埋下伏笔。

## 11.4 选对第一个场景：首战必胜

### 第一个场景的重要性

在企业客户中，Agent 的第一个场景至关重要。它决定了客户对 Agent 的第一印象，决定了后续能否扩展到更多场景，也决定了这个客户能否成为标杆案例。**首战必胜**是 Agent 企业销售的铁律。

### 第一个场景的选择标准

选择第一个场景时，建议遵循以下标准：

1. **是黄金任务**：高频、高价值、易验证、可容错（见第 4 章）。
2. **有积极的业务负责人**：有一位愿意投入时间、愿意推动变化的业务负责人。没有业务负责人的项目，往往会变成 IT 部门的"技术试验"，难以产生真正的业务价值。
3. **数据和系统条件具备**：不需要大规模的数据治理和系统改造就能开始。
4. **结果可量化**：能够用清晰的指标来衡量 Agent 带来的价值。
5. **能在六到八周内见效**：周期太长，客户会失去耐心，领导层的关注也会转移。
6. **失败不致命**：即使效果不如预期，也不会对客户的业务造成严重影响。
7. **有扩展潜力**：成功之后，能够自然地扩展到更多的场景、部门或业务单元。

### 警惕"最难的场景"

有些客户会说："你们先把我们最难的问题解决了，我们就相信你们。"这种要求看似合理，实则危险。最难的问题往往是因为数据条件差、流程复杂、风险高、涉及多个部门——这些恰恰是 Agent 最难成功的条件。

面对这种要求，建议的回应是："我们非常理解您希望看到 Agent 解决最难的问题。我们的经验是，先从一个更容易成功的场景开始，让团队熟悉 Agent 的工作方式，积累数据和经验，然后再挑战更难的问题，成功率会高得多。我们可以把最难的问题列为第二阶段的目标。"

## 11.5 POC：把试点做成"小项目"

### POC 在 Agent 销售中的地位

POC（概念验证，Proof of Concept）在传统软件销售中也很常见，但在 Agent 销售中尤为关键。在第 3 章，我们把"试点上岗"列为 Agent 九站旅程中比 SaaS 多出来的一站。客户不会因为一个演示就相信 Agent 能在自己的业务中干活，他们需要看到 Agent 在真实环境中、处理真实任务的表现。

### 三段式 POC

我们建议把 POC 设计为三个阶段：**对齐、执行、复盘**。

#### 第一阶段：对齐（1–2 周）

对齐阶段的核心产出是一份 **POC 成功标准书**，双方共同签字确认。这份文件应该包括：

- **POC 目标**：通过这次 POC，要验证什么？
- **场景与范围**：具体在哪个场景、处理哪些任务、涉及哪些数据和系统、多少用户参与。
- **成功标准**：用哪些指标来判断 POC 是否成功？每个指标的目标值是多少？如何测量？
- **双方的责任**：供应商负责什么？客户负责什么（比如提供数据、提供环境、安排人员参与、及时反馈）？
- **时间计划**：每个阶段的时间节点。
- **决策规则**：POC 成功后，下一步是什么？比如"如果达到成功标准，双方将在 XX 时间内启动采购流程"。

最后一条特别重要。很多 POC 做完了，效果也不错，但客户迟迟不做决策，项目就这样搁置了。在 POC 开始之前就约定好"成功之后怎么办"，可以有效避免这种情况。

#### 第二阶段：执行（4–6 周）

执行阶段的核心是**快速迭代、紧密沟通**：

- **每周例会**：与客户的业务负责人和关键用户每周开一次例会，回顾进展、讨论问题、调整方向。
- **快速响应**：对客户反馈的问题快速响应和修复。
- **数据记录**：系统地记录 Agent 的表现数据，为复盘阶段做准备。
- **用户参与**：确保客户的一线用户真正参与到 POC 中，使用 Agent 处理真实的工作。
- **问题透明**：遇到问题时，及时、坦诚地与客户沟通，而不是隐瞒或拖延。

#### 第三阶段：复盘（1 周）

复盘阶段的核心产出是一份 **POC 价值报告**，包括：

- **成果总结**：POC 期间 Agent 完成了多少任务，各项指标的达成情况。
- **价值测算**：基于 POC 数据，测算全面推广后可能带来的价值（时间节省、成本节省、质量提升等）。
- **用户反馈**：一线用户的使用体验和反馈。
- **问题与改进**：POC 中遇到的问题，以及后续的改进计划。
- **推广建议**：全面推广的路线图、资源需求、预算建议。

这份报告不仅是给客户决策者看的，也是**给客户内部的发起者用来向上汇报的**。所以报告要写得清晰、专业、有说服力，让发起者拿着它去汇报时"有面子"。

### POC 常见陷阱

**陷阱一：无限期 POC。**POC 没有明确的时间限制，一拖再拖，最后不了了之。解决方法：在成功标准书中明确时间节点和决策规则。

**陷阱二：免费 POC 不被珍惜。**客户不需要付出任何成本，就不会认真对待，不会投入人力配合。解决方法：考虑收费 POC，或者至少要求客户投入明确的人力和资源。在中国市场，收费 POC 的接受度在逐步提高，尤其是对于需要较多实施工作的项目。一种常见的做法是：POC 收取一定费用，如果后续正式采购，POC 费用可以抵扣合同金额。

**陷阱三：指标后移。**POC 达到了最初约定的成功标准，客户却提出新的、更高的要求。解决方法：成功标准书由双方签字确认；如果客户确实有新的需求，作为下一阶段的目标，而不是否定当前的 POC 结果。

**陷阱四：只有 IT 参与。**POC 由客户的 IT 部门主导，业务部门没有真正参与，最终 IT 部门说"技术上可行"，但业务部门说"不知道有什么用"。解决方法：确保业务负责人和一线用户深度参与 POC。

**陷阱五：演示数据与真实数据。**POC 使用的是经过清洗的样本数据，效果很好，但正式上线后面对真实的、杂乱的数据，效果大打折扣。解决方法：尽量在 POC 中使用真实数据，至少是有代表性的真实数据样本。

**陷阱六："POC 地狱"。**客户同时与多家供应商做 POC，或者反复要求做不同场景的 POC，供应商投入大量资源，却始终无法进入采购阶段。解决方法：在投入 POC 之前，评估客户的采购意向和预算情况；限制免费 POC 的范围和次数；对于明显只是在"收集信息"的客户，提供标准化的演示而不是定制化的 POC。

## 11.6 方案与演示

### 定制化演示

在企业销售中，通用的产品演示往往不够有说服力。建议尽量做**定制化演示**：使用客户行业的场景、客户类似的数据（脱敏或模拟）、客户熟悉的术语。如果客户愿意提供一些样本数据，用客户自己的数据做演示，效果最好。

### 方案书结构

一份好的 Agent 解决方案书，建议包括以下部分：

1. **客户现状与挑战**：用客户的语言描述客户面临的问题，让客户感到"你懂我"。
2. **解决思路**：Agent 如何解决这些问题，人与 Agent 如何分工协作。
3. **Agent 岗位说明书**：Agent 在这个场景中承担的具体职责、权限和考核指标（见第 4 章）。
4. **技术方案**：部署架构、系统集成、数据流向、安全措施。
5. **实施计划**：从 POC 到全面推广的路线图和时间表。
6. **价值测算**：预期带来的价值和投资回报。
7. **成功案例**：同行业或类似场景的成功案例。
8. **服务保障**：服务团队、服务等级、培训计划。
9. **商务方案**：报价、付款方式、合同条款要点。
10. **公司介绍与资质**：公司背景、资质认证、合规情况。

## 11.7 商务谈判

### Agent 合同中需要特别关注的条款

Agent 合同除了传统软件合同的常规条款外，还有一些需要特别关注的条款：

**数据条款**：
- 客户数据的所有权归属；
- 数据的使用范围（是否用于模型训练、是否用于产品改进）；
- 数据的存储位置和期限；
- 合同终止后的数据返还和删除。

**责任条款**：
- Agent 出错时的责任划分；
- 供应商的责任上限；
- 客户的配合义务（如结果审核、权限配置）。

**服务等级条款**：
- 系统可用性承诺；
- 问题响应和解决时间；
- 性能指标（如任务处理时间）；
- 未达到服务等级时的补偿方式。

**知识产权条款**：
- Agent 产出物（如生成的代码、文档、报告）的知识产权归属。通常约定归客户所有，但需要明确。
- 定制开发部分的知识产权归属。
- 客户提供的数据、知识、流程的知识产权保护。

**模型变更条款**：
- 供应商更换底层模型时，是否需要通知客户？
- 模型变更导致效果下降时，如何处理？

### 中国企业常见的付款方式

中国企业的软件采购，常见的付款方式包括：

- **预付款 + 验收款 + 尾款**：比如签约后支付一部分，验收后支付大部分，质保期结束后支付尾款。
- **按年预付**：订阅类产品按年预付。
- **按里程碑付款**：项目类合同按照约定的里程碑分期付款。

需要注意的是，中国企业（尤其是大型企业和国企）的付款周期往往较长，验收流程也较为复杂。在谈判中要尽量明确验收标准和付款时间，并做好资金规划。

### 验收标准

对于 Agent 项目，验收标准的设定尤其重要，也尤其困难。传统软件的验收主要看"功能是否实现"，而 Agent 的验收需要看"效果是否达到"。建议：

- 验收标准尽量量化，并与 POC 成功标准衔接；
- 区分"功能验收"（系统部署完成、功能可用）和"效果验收"（达到约定的效果指标），两者可以分开进行；
- 效果验收要考虑到 Agent 的效果需要一定时间的运行和优化才能稳定，避免在上线初期就进行效果验收。

## 11.8 应对常见异议

以下是 Agent 企业销售中最常见的十种异议，以及建议的回应思路：

| 异议 | 背后的担忧 | 回应思路 |
|---|---|---|
| "AI 不靠谱，会胡说八道" | 能力可信 | 承认风险，展示验证机制和"人在回路"设计，用真实数据说话 |
| "我们的数据不能出去" | 数据安全 | 提供私有化部署方案，展示数据流向图 |
| "大厂的产品免费，你们为什么收费" | 价格 | 比较净交付价值，而不是比较价格；展示专业场景下的差异 |
| "我们再等等，技术还在快速变化" | 时机 | 强调先行者的学习曲线优势；提供低风险的起步方式；说明产品会随模型升级持续变强 |
| "员工不会用 / 不愿意用" | 组织变革 | 提供培训和变革管理支持；强调"减负"而非"替代"；分享其他客户的推广经验 |
| "我们的情况很特殊" | 适配性 | 承认差异，提出用 POC 验证；展示类似复杂场景的案例 |
| "你们公司太小了 / 太新了" | 供应商可持续性 | 展示融资情况、客户情况、团队背景；提供数据迁移和退出方案 |
| "出了问题谁负责" | 责任归属 | 说明合同中的责任划分；展示控制机制和审计能力 |
| "和我们现有系统打不通" | 集成 | 展示集成能力清单和标准协议支持；评估具体的集成工作量 |
| "预算今年已经用完了" | 预算 | 了解下一个预算周期；提出今年先做小规模 POC，为明年的预算申请准备数据 |

应对异议的总体原则是：**不要急于反驳，先理解异议背后的真正担忧，然后针对担忧提供证据和方案。**很多时候，客户说出口的异议并不是真正的原因，需要通过追问找到背后的担忧。

## 11.9 从试点到规模化

### 规模化是 Agent 项目最难的一关

很多 Agent 项目在试点阶段效果很好，但在规模化推广时遇到了困难：

- 试点中有专门的团队支持，规模化后支持力量被摊薄；
- 试点中参与的是积极的早期用户，规模化后面对的是更多观望甚至抵触的用户；
- 试点中处理的是精选的任务，规模化后面对的是更多样、更复杂的任务；
- 试点中的成功经验没有被系统地总结和复制。

### 规模化路线图

建议在试点成功后，与客户共同制定一份规模化路线图，通常包括三个方向的扩展：

**横向扩展：更多用户。**在同一个场景中，从试点的少数用户扩展到全部相关用户。比如从两名会计扩展到整个财务部。

**纵向扩展：更多任务。**在同一个部门中，从试点的单一任务扩展到更多相关任务。比如从对账扩展到发票审核、费用报销审核。

**跨部门扩展：更多场景。**从一个部门扩展到其他部门。比如从财务部扩展到采购部、人力资源部。

### 变革管理

规模化推广的核心挑战往往不是技术，而是**人**。需要系统的变革管理：

- **沟通愿景**：让员工理解为什么要引入 Agent，Agent 会如何改变他们的工作，强调 Agent 是来帮助而不是取代他们。
- **培训赋能**：为员工提供系统的培训，让他们学会与 Agent 协作，成为合格的"AI 管理者"。
- **树立榜样**：让试点中的积极用户分享经验，成为推广的榜样。
- **调整激励**：调整考核和激励机制，鼓励员工使用 Agent、提升效率。如果员工因为使用 Agent 提高了效率，反而被分配更多的工作而没有任何回报，他们就没有动力使用 Agent。
- **岗位重塑**：帮助企业重新设计受 Agent 影响的岗位，让员工从重复性工作转向更有价值的工作。

### AI 卓越中心

对于大型企业客户，建议推动建立企业内部的"**AI 卓越中心**"（AI Center of Excellence）——一个跨部门的团队，负责企业 AI 应用的规划、推广、治理和经验沉淀。AI 卓越中心是 Agent 在企业内部规模化推广的组织保障，也是供应商在客户内部最重要的合作伙伴。

## 11.10 大客户经营

对于重要的企业客户，需要建立系统的大客户经营机制：

- **客户成功计划**：为每个大客户制定年度的客户成功计划，明确目标、里程碑和行动。
- **季度业务回顾**：每季度与客户的业务负责人和决策者进行一次业务回顾，展示 Agent 带来的价值，讨论下一步的计划。
- **高层对话**：定期安排供应商高层与客户高层的对话，了解客户的战略方向，探讨更深层次的合作。
- **客户顾问委员会**：邀请重要客户加入客户顾问委员会，参与产品规划的讨论。

我们会在第 15 章更详细地讨论客户成功。

## 11.11 案例：一家物流企业的运维 Agent 之路

> 以下为综合化、匿名化案例，公司名为化名，数字为示意。

"捷通物流"是一家全国性的物流企业，拥有庞大的信息系统。其 IT 运维团队每天要处理大量的告警和工单，人手长期紧张，夜间值班尤其辛苦。

**线索与诊断**。捷通物流的 IT 运维负责人老周在一次技术大会上听了"智维科技"的演讲，介绍了运维 Agent 在告警分析和故障处理中的应用。会后，老周主动联系了智维。智维的解决方案架构师用了两次会议进行诊断，了解到：捷通每天有数千条告警，其中大量是重复告警和误报；运维人员处理一个工单平均需要较长时间，大部分时间花在查日志、查监控、查变更记录上；夜间值班人员只有两人，经常应接不暇。

**场景选择**。根据诊断结果，智维建议第一个场景选择"**告警分析与初步诊断**"：Agent 自动分析告警，过滤重复和误报，对真实告警进行初步诊断（查日志、查监控、查最近的变更），生成诊断报告，推送给值班人员。Agent 不执行任何修复操作，只提供诊断建议。这个场景满足了首战必胜的标准：高频、价值明确、结果可验证（诊断是否正确可以由运维人员判断）、风险可控（Agent 只读不写）、有积极的业务负责人。

**POC**。双方签署了 POC 成功标准书，约定了三个指标：告警降噪率、诊断准确率、平均诊断时间。POC 为期六周，在捷通的一个核心业务系统上进行。前两周，Agent 的诊断准确率不够理想，主要原因是对捷通的系统架构和历史故障缺乏了解。智维的前线部署工程师与捷通的运维人员一起，整理了系统架构文档、历史故障案例和运维手册，作为 Agent 的知识库。第三周开始，诊断准确率明显提升。六周结束时，三个指标都达到了约定的目标。

**签约**。POC 价值报告显示，如果全面推广，可以显著减轻运维人员的工作负担，尤其是夜间值班的压力。老周拿着这份报告向 CIO 汇报，CIO 批准了采购。由于捷通对数据安全有较高要求，最终采用了私有化部署方案，底层使用了在捷通内网部署的开源模型。

**规模化**。上线后，智维与捷通共同制定了规模化路线图：第一阶段扩展到全部核心业务系统；第二阶段增加"常见故障自动处理"能力——对于有标准处理流程的常见故障，Agent 在获得值班人员一键确认后自动执行处理；第三阶段扩展到变更风险评估。在第二阶段，双方特别设计了渐进式放权路径：先是 Agent 给出处理方案、人工执行；然后是 Agent 执行、每一步人工确认；最后对于少数低风险、高频的故障，Agent 可以在人工一键授权后自动完成处理。

**成果**。一年后，捷通的运维团队工作方式发生了显著变化：值班人员不再被大量的告警淹没，而是把精力集中在 Agent 无法处理的复杂问题上；故障的平均处理时间明显缩短；运维人员的满意度也有了提升。老周在一次行业会议上分享了这个案例，为智维带来了多个新的线索。

### 案例启示

1. **诊断先行**，帮助客户选对第一个场景。
2. **"只读不写"的第一个场景**大大降低了风险，提高了成功率。
3. **前线部署工程师**是 POC 成功的关键，知识库的建设往往决定了 Agent 的效果。
4. **POC 价值报告**是推动客户决策的重要工具，要让发起者"有面子"。
5. **渐进式放权**让客户在信任建立的过程中逐步扩大 Agent 的权限。
6. **满意的客户会成为最好的销售**。

## 本章要点

1. Agent 企业销售的终点是"上岗"而不是签约。销售团队需要客户经理、解决方案架构师、前线部署工程师、客户成功经理紧密协作。
2. 线索来源中，老客户推荐和自下而上信号的质量最高。
3. 诊断先行：用诊断问题清单了解任务、现状、数据与系统、组织、预算与时间；用适配度评估表判断是否适合。拒绝不适合的项目比接下注定失败的项目更有价值。
4. 第一个场景要首战必胜：黄金任务、有积极的业务负责人、条件具备、结果可量化、六到八周见效、失败不致命、有扩展潜力。警惕"最难的场景"。
5. 三段式 POC：对齐（成功标准书）、执行（快速迭代、紧密沟通）、复盘（价值报告）。警惕六大 POC 陷阱。
6. Agent 合同要特别关注数据、责任、服务等级、知识产权、模型变更条款。验收要区分功能验收和效果验收。
7. 应对异议的原则：先理解背后的担忧，再针对担忧提供证据和方案。
8. 规模化是最难的一关：横向、纵向、跨部门扩展；系统的变革管理；推动建立 AI 卓越中心。
